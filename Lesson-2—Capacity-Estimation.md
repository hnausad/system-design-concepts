# Lesson 2 — Capacity Estimation

Capacity estimation is one of the **most important skills for a senior system-design interview**.

The goal is not to produce perfectly accurate numbers.

The goal is to show:

> **"I can translate business requirements into approximate infrastructure requirements."**

For example:

```text
10 million users
       ↓
Daily activity
       ↓
Requests/day
       ↓
Average QPS
       ↓
Peak QPS
       ↓
Servers / DB / Cache / Queue
```

---

# 1. Why Do We Need Capacity Estimation?

Suppose an interviewer says:

> Design a ride-sharing system.

If you don't know the traffic, you don't know whether you need:

```text
1 server
```

or:

```text
100 servers
```

or:

```text
1000+ servers
```

Similarly, you can't intelligently decide:

* SQL vs NoSQL
* Number of database replicas
* Cache size
* Kafka partitions
* Number of application instances
* Sharding strategy
* Network bandwidth
* Storage requirements

So capacity estimation comes **before detailed architecture**.

---

# 2. The Numbers You Need

For most interviews, estimate these:

```text
1. Users
2. DAU
3. Requests/day
4. Average QPS
5. Peak QPS
6. Read QPS
7. Write QPS
8. Storage
9. Storage growth
10. Bandwidth
11. Cache requirements
```

You don't always need every number.

Focus on numbers that influence the architecture.

---

# 3. Start With Users

Suppose interviewer gives:

```text
Total users = 100 million
DAU = 10 million
```

Don't immediately use 100M for traffic.

Usually:

```text
Total users
     ↓
Daily Active Users
     ↓
Requests generated by DAU
```

So:

```text
DAU = 10M
```

is more useful for estimating daily traffic.

---

# 4. Requests Per User

Suppose each active user makes:

```text
20 requests/day
```

Then:

```text
10M users × 20 requests
```

= **200M requests/day**

So:

```text
Requests/day = 200 million
```

---

# 5. Convert Requests/Day → QPS

This is one formula you should memorize:

```text
Average QPS =
Requests per day / 86,400
```

Because:

```text
1 day = 24 × 60 × 60
      = 86,400 seconds
```

Therefore:

```text
200,000,000 / 86,400
≈ 2,315 QPS
```

So our average traffic is approximately:

> **2.3K requests/sec**

---

# 6. Peak QPS

Real systems don't receive requests uniformly.

For example:

```text
             Traffic
                │
                │       /\
                │      /  \
                │     /    \
                │____/      \____
                │
                └────────────────── Time
```

There are peak periods.

In interviews, you can assume:

```text
Peak = 5× to 10× average
```

Suppose we use 10×:

```text
Peak QPS
= 2,315 × 10
≈ 23,150 QPS
```

So:

```text
Average QPS ≈ 2.3K

Peak QPS ≈ 23K
```

Now we have something useful for architecture.

---

# 7. Read vs Write QPS

Suppose our system is:

```text
90% reads
10% writes
```

Total peak:

```text
23,150 QPS
```

### Read QPS

```text
23,150 × 90%
≈ 20,835
```

### Write QPS

```text
23,150 × 10%
≈ 2,315
```

So:

```text
Peak
│
├── Read ≈ 20.8K QPS
└── Write ≈ 2.3K QPS
```

Now architectural decisions become much easier.

We might need:

```text
Cache
Read replicas
Horizontal application scaling
Write-optimized database
```

---

# 8. Storage Estimation

Now let's estimate storage.

Suppose:

```text
10M new records/day
```

Each record is approximately:

```text
1 KB
```

Then:

```text
10M × 1 KB
= 10 GB/day
```

Monthly:

```text
10 GB × 30
≈ 300 GB/month
```

Yearly:

```text
300 GB × 12
≈ 3.6 TB/year
```

So:

```text
Daily     ≈ 10 GB
Monthly   ≈ 300 GB
Yearly    ≈ 3.6 TB
```

This is raw data.

Real storage requirements are usually higher because of:

* Indexes
* Replicas
* Metadata
* Backups
* Logs
* Temporary storage

For interview estimation, state your assumption.

---

# 9. The 2× Rule

You don't need excessive precision.

If your calculation gives:

```text
3.6 TB/year
```

you can say:

> "Approximately 4 TB/year of raw data. With indexes, replication, and operational overhead, I'd provision significantly more."

That's much better than spending five minutes calculating:

```text
3.627891 TB
```

😂

System design estimation is about **order of magnitude**.

---

# 10. Bandwidth Estimation

Suppose every request returns:

```text
20 KB
```

and peak traffic is:

```text
20,000 requests/sec
```

Then:

```text
20,000 × 20 KB
= 400,000 KB/sec
```

Approximately:

```text
400 MB/sec
```

Convert to bits:

```text
400 MB × 8
≈ 3.2 Gbps
```

So you need roughly:

> **3.2 Gbps outgoing bandwidth**

This becomes important for systems like:

* Video streaming
* Image delivery
* File downloads
* Social media feeds

---

# 11. API-Specific QPS

This is a very useful senior-level technique.

Don't only calculate:

```text
Total QPS
```

Break it down.

Suppose:

```text
10M DAU
20 requests/user/day
200M requests/day
```

But those requests could be:

```text
Product Search       40%
Product Details      30%
Cart                 10%
Orders               10%
Other                10%
```

Then:

```text
Total average QPS ≈ 2,315
```

Therefore:

```text
Search:
2315 × 40%
≈ 926 QPS

Product:
2315 × 30%
≈ 695 QPS

Cart:
2315 × 10%
≈ 232 QPS

Orders:
2315 × 10%
≈ 232 QPS
```

This tells us where the real bottlenecks are likely to be.

---

# 12. Capacity Estimation Example — URL Shortener

Let's do a complete interview-style example.

### Requirement

> Design a URL shortener like Bitly.

Assume:

```text
100M registered users
10M DAU
```

Suppose:

```text
Each user creates 2 shortened URLs/day
```

Then:

```text
10M × 2
= 20M URLs/day
```

So:

> **20 million writes/day**

---

# 13. Write QPS

```text
20M / 86,400
≈ 231 writes/sec
```

Average:

```text
≈ 230 writes/sec
```

Assume peak = 10×:

```text
≈ 2,300 writes/sec
```

That's manageable for many database architectures.

---

# 14. Read QPS

Now suppose each shortened URL is accessed 20 times/day.

```text
20M URLs × 20
= 400M redirects/day
```

Average:

```text
400M / 86,400
≈ 4,630 reads/sec
```

Peak:

```text
≈ 46,300 reads/sec
```

Now look at the architecture:

```text
              Users
                |
                ↓
          Load Balancer
                |
                ↓
        URL Redirect Service
                |
                ↓
             Redis
             /   \
            /     \
        Cache Hit  Miss
                    |
                    ↓
                 Database
```

Why Redis?

Because:

```text
Read QPS ≈ 46K
Write QPS ≈ 2.3K
```

It's heavily read-oriented.

That's a **capacity-driven architectural decision**.

---

# 15. Storage for URL Shortener

Suppose each URL record consumes approximately:

```text
500 bytes
```

20M new URLs/day:

```text
20M × 500 bytes
= 10 GB/day
```

Year:

```text
10 × 365
≈ 3.65 TB/year
```

Again:

> Approximately 3.7 TB/year raw storage.

Add:

```text
Indexes
Replication
Backups
Metadata
```

and actual infrastructure storage will be higher.

---

# 16. Capacity Estimation for Ride Sharing

Let's connect this to the system we discussed in Lesson 1.

Suppose:

```text
50M registered users
10M DAU

2M active rides/day
```

Now think about the operations:

```text
Request Ride
Driver Location Update
Find Nearby Drivers
Accept Ride
Trip Status Update
Payment
```

The important insight is:

> **Not every operation has the same traffic pattern.**

Driver location updates may dominate.

Suppose:

```text
1M active drivers
```

and each sends a location update every:

```text
5 seconds
```

Then:

```text
1M / 5
= 200,000 location updates/sec
```

🔥 Now we've discovered a very important architectural requirement:

> **200K writes/sec just for location updates.**

This could completely change the design.

We probably don't want:

```text
200K writes/sec
       ↓
Traditional relational DB
```

for every GPS update.

Instead we might consider:

```text
Drivers
   |
   ↓
Location Service
   |
   +---- In-memory/geospatial store
   |
   +---- Event stream
```

This is why capacity estimation matters.

---

# 17. Estimation Can Change the Architecture

This is the key lesson.

Before estimation:

```text
Location
   ↓
Database
```

After estimation:

```text
200K updates/sec
```

Now we think:

```text
Do we need:
- Partitioning?
- In-memory storage?
- Geospatial indexing?
- Kafka?
- Data expiration?
- Batching?
- Multiple location servers?
```

**Numbers drive architecture.**

---

# 18. Important Formulas to Memorize

Keep these handy:

### Requests/day

```text
DAU × requests/user/day
```

### Average QPS

```text
Requests/day ÷ 86,400
```

### Peak QPS

```text
Average QPS × Peak Factor
```

Usually:

```text
5×–10×
```

when no better information is available.

### Read QPS

```text
Total QPS × Read %
```

### Write QPS

```text
Total QPS × Write %
```

### Storage

```text
Records/day × Record Size
```

### Yearly Storage

```text
Daily Storage × 365
```

### Bandwidth

```text
Requests/sec × Response Size
```

Then:

```text
Bytes/sec × 8
= bits/sec
```

---

# 19. Quick Estimation Cheat Sheet

Memorize:

```text
1K       = 1,000
1M       = 1,000,000
1B       = 1,000,000,000

1 day    = 86,400 sec
1 month  ≈ 30 days
1 year   ≈ 365 days
```

For quick interview math:

```text
1M requests/day
≈ 12 QPS

10M requests/day
≈ 116 QPS

100M requests/day
≈ 1,157 QPS

1B requests/day
≈ 11,574 QPS
```

This shortcut is extremely useful.

---

# 20. What Interviewers Are Looking For

They are **not** checking whether you can do complex mathematics.

They're looking for:

### ① Clear assumptions

> "I'll assume 10M DAU."

### ② Simple calculations

> "10M users × 20 requests/day = 200M requests/day."

### ③ Order of magnitude

> "That's roughly 2K average QPS and 20K peak QPS."

### ④ Architectural implications

> "Since reads dominate, I'll introduce caching and read replicas."

### ⑤ Awareness of uncertainty

> "These are estimates; I'd validate them using production metrics."

That's a strong senior answer.

# 22. One Senior-Level Rule

Don't estimate everything.

Suppose you're designing a URL shortener.

The important numbers are:

```text
URL creation QPS
Redirect QPS
Storage
Cache
```

You probably don't need to calculate:

```text
CPU cycles per request
Exact network packets
Exact RAM per JVM
```

unless the interviewer asks.

Always ask:

> **"Which number will influence my architecture?"**

That's the mindset I want you to develop.
